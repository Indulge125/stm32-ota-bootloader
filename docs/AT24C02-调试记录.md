## 一、为什么先造工具，而不是先改代码

AT24C02 是通过软件 I2C 访问的，而 `IIC_Receive_Ack()` 只有两种结果：收到应答 / 没收到。
**"没收到"这一个 bit 背后可能是十几种完全不同的硬件原因** —— 线没接、接反、短路、器件没电、
器件地址不对、写保护、芯片没插好……

第一版自检只打印了一个 `ERR`。它证明了"失败了"，但对"为什么"零信息量。
所以第一步不是改驱动，而是**把"没应答"拆成可判定的几类**，每一类对应一个明确的下一步动作。

这一步是整个排查里最值得投入的地方：它把后续每一次 "改代码 → 编译 → 烧录 → 看现象" 的
一次试错，变成了**一次就能拿到一条确定结论**。

## 二、诊断设计

围绕 I2C 的两个电气特性做文章：

1. **I2C 必须用开漏输出**，所以引脚配上开漏后，**释放总线（写 1）时读回的就是线上真实电平**。
2. **板载上拉电阻通常是 4.7 kΩ，而 STM32 内部上下拉约 40 kΩ。** 两者较量时外部完胜 ——
   于是"把引脚临时改成内部下拉/上拉输入再读"，就能反过来推断线上挂了什么。

由此得到三个探针：

| 探针 | 做法 | 判据 |
|---|---|---|
| `MyIIC_ReadIdleLevel()` | 释放总线后读回电平 | 哪条读到 0，说明它被拉死 |
| `MyIIC_ProbeExternalPullup()` | 改成**内部下拉**输入再读 | 读到 1 → 该线挂着外部上拉，即器件确实接在这一脚 |
| `MyIIC_ProbeForcedLow()` | 改成**内部上拉**输入再读 | 读到 0 → 该线被硬拉在地（短到 GND） |

后两个配合，能把一条线的状态判成三种：**正常 / 悬空 / 短到 GND**。

再加两个扫描手法：

- **全地址扫描**（0x01~0x7F）：器件地址由 A0/A1/A2 决定。**地址接错不会让器件消失，
  只会让它搬到别的地址去** —— 扫一遍就知道它在哪。
- **SCL/SDA 角色对调后再扫**：`MyIIC_SwapPins()` 在运行期交换两个引脚的角色。
  若对调后能扫到器件，就说明**两根线物理上接反了 —— 不动硬件也能判定**。

## 三、证据链

每一轮都是"发现问题 → 加一个探针 → 拿到一条确定结论"：

| 轮次 | 本轮新增的诊断能力 | 实测输出 | 排除掉的可能 |
|---|---|---|---|
| 1 | 读写回环 + JEDEC ID | `MID:EF DID:4017` `EE24C02:ERR` `Flag:00000000` | —（只知道失败） |
| 2 | 空闲电平 + 全地址扫描 + 返回码 | `SCL:1 SDA:1` `Scan:0` `W:1` `R:1` | 总线被拉死；WP 写保护（WP 高时器件照样应答） |
| 3 | 外部上拉探针 | `Scan:0` `Probe:3` | 模块没接上 / 没供电 |
| 4 | 角色对调扫描 + 短接检测 | `Idle:1 Prb:1` `Scan:0` `Swp:7 02` `Sh:1` | 此轮线路已损坏，结果不可信 |
| 5 | 拉地探针 | `Idle:3 Prb:3` `Scan:1 Swp:0` `Sh:0` | 线没接好；SCL/SDA 接反；两根线短接 |
| 6 | （修显示缺陷） | `Scan:1 0xAE` | 器件存在，但地址不是 0xA0 |
| 7 | — | `EE24C02:OK` `Flag:FFFFFFFF` | — |

**第 2 轮就有个关键推论**：`Flag` 显示 `00000000` 而不是 `FFFFFFFF`。
全新 EEPROM 每个字节都是 `0xFF`；读操作根本没把数据写进缓冲区（`memset` 的 0 留了下来），
所以**读通路从未成功过**。这一步把"读出来是 0"和"读取失败"区分开了 —— 只差一个字节的观察，
但排除了"读通了但内容恰好是 0"这条岔路。

**第 6 轮的 `0xAE` 信息量最大**：AT24C02 的器件地址是 `1010 A2 A1 A0 R/W`，
`0xAE = 1010 111 0`，即 **A2/A1/A0 三位全是 1**。

## 四、根因

### 1. 地址跳线帽方向错误（已确证）

模块的 `A0 / A1 / A2 / WP` 各是一组**三针跳线块**：中间那针连芯片管脚，两侧分别接 VCC 和 GND。
跳线帽跨哪两针，就把该位拉成哪边的电平。当时四个帽子都跨在 **VCC 侧**，于是：

- A2/A1/A0 = 111 → 器件地址变成 **`0xAE`**，而代码里写死的是 `0xA0` → 永远不应答
- WP = 1 → **写保护生效**

**WP 拉高的现象特别隐蔽**：器件照样 ACK，`WriteByte` / `ReadData` 的返回码全是 0，
看起来"读写都正常"，但数据写不进存储阵列 —— 表现为"不报错却读不回"。
如果没提前知道这一点，很容易在这一步卡死。

**修复**：四个跳线帽全部挪到 GND 侧。地址变回 `0xA0`，写保护解除。

### 2. SCL/SDA 走线异常（推断，无法归因到具体哪一项）

在第 2~3 轮，下列条件同时成立：

- 模块在电气上确实接在两个引脚上（`Probe:3`）
- 模块供电正常（板载电源指示灯亮）
- 总线电平正常（`SCL:1 SDA:1`）、时序正常（`Delay_us` 实测 10 µs，SCL ≈ 50 kHz）
- **但器件在 128 个地址上一个都不应答**

"线接着、电有、电平对，却完全不应答"——这只能是协议层收不到有效波形。
重新接线后器件上线，所以问题出在走线上。

**但具体是"SCL/SDA 接反"还是"杜邦线本身不良"，已经无法判定** ——
当时为了省一轮试错，我把"对调两根线"和"检查/更换杜邦线"放到了同一轮里做，
**一次改了两个变量**，事后就失去了归因能力。这是本次排查里最该记住的教训。

### 3. 杜邦线接触不良（已确证）

重新接线过程中，PB10（SCL）一度完全掉线：`Idle:1 Prb:1` —— 释放后读到 0，
且探不到任何外部上拉。更换该杜邦线后恢复。

**值得注意**：第 2~3 轮 `Probe:3` 显示两条线都"正常"，但探针只验证"线接通了"，
**不验证信号完整性**——4.7 kΩ 上拉只需微安级电流就能把线拉高，而 I2C 传输时器件要把线
快速拉低，接触不良（接触电阻大 / 寄生电容大）的线能通过探针却带不动有效低电平。
**探针报"正常"不等于这条线能通信用。**

## 五、诊断工具自身的三个缺陷

这三条都是排查过程中实际踩到的，也是这套工具能收敛的原因之一 ——
**如果连"测量工具本身可不可信"都没验证过，后面所有结论都站不住。**

### 1. 短接检测缺少前提校验，产生假警报

初版逻辑是"拉低 SCL，看 SDA 是否跟着变低"。但**如果 SCL 本来就是低的**
（比如那根线已经掉到地上），"跟着变低"恒成立，于是报出假短接（`Sh:1`）。

**修正**：先确认两根线都能释放为高，否则返回 `0x04` 表示"测试无效"。

### 2. 关键信息被放在了错误的分支里

把"显示器件地址"写进了 `if(n2 > 0)` 分支。结果**常规扫描找到器件时**（此时 `n2` 恒为 0），
**最该看到的地址反而被隐藏了** —— 连续两轮只能看到 `Scan:1` 却不知道在哪个地址。
修正后：常规扫描有结果就显示它的地址，只有常规扫描为空时才显示对调扫描的结果。

### 3. 基于单一数据点过早排除假设

第 2 轮时曾据"`Flag` 是 0 而不是 `FFFFFFFF`"推断 **WP 写保护不成立**。
这个推理的前提是"读操作成功了"，可实际上读操作因为**地址不对**本来就在失败，
`memset` 的 0 从未被覆盖 —— **那条证据对 WP 什么也没证明**。

后来 WP 恰恰也是问题之一。教训：**排除一个假设，必须确认所用的证据真的能被该假设影响。**

## 六、可复用的检查清单

下次遇到软件 I2C 器件不应答，按这个顺序查：

1. **空闲电平对不对？** 两条线释放后都该是高。哪条低 → 被拉死 / 短路 / 上拉缺失
2. **线到底接上没有？** 内部下拉探针：读到 1 = 挂着外部上拉 = 真的接上了
3. **是悬空还是短到地？** 内部上拉探针：拉不起来 = 短到 GND
4. **器件在哪个地址？** 全地址扫描。**扫不到时先确认线是好的再下结论** ——
   悬空的线读回随机值会产生假应答，扫描结果不可信
5. **是不是接反了？** 角色对调后再扫。扫到 = 接反
6. **两根线短接没有？** 但要先确认两线都能为高，否则误报
7. **地址跳线块方向对不对？** 三针块：中间是信号，两侧是 VCC / GND，帽子跨哪边就是哪个电平

**贯穿全程的原则**：每次只改一个变量。同时改两处，就算修好了也不知道是哪一处起了作用。

## 七、复盘

**做对的地方**

- 先造测量工具再动手改，把"猜"换成了"读数据"
- 每一步都保留完整的原始输出，事后能回溯每条结论的依据
- 探针的设计直接利用器件电气特性（开漏可读回、内外上拉强弱对比），而不是靠试

**做得不够的地方**

- **第 2~3 轮就该意识到"探针报正常"不等于"信号完整性正常"**，
  早一点怀疑杜邦线，能少绕两轮
- **同一轮里改了两个变量**，导致根因 2 永远无法确认
- 诊断的输出信息没有一开始就设计周全（地址被藏在错误分支里）

## 附录：探针实现要点

```c
/* 原理：开漏输出模式下 GPIO 的输入通路仍然有效，所以把线释放为高后能读回真实电平 */

/* 探针 1：空闲电平 */
uint8_t MyIIC_ReadIdleLevel(void)
{
    MyIIC_W_SCL(1);
    MyIIC_W_SDA(1);
    Delay_us(10);
    /* 读回两条线：bit1 = SCL，bit0 = SDA，正常应为 3 */
}

/* 探针 2：外部上拉 —— 把引脚改成内部下拉输入（约 40kΩ）。
 * 模块上拉一般 4.7kΩ，能压过内部下拉 → 读到 1 说明该线确实挂着外部上拉 */
uint8_t MyIIC_ProbeExternalPullup(void)
{
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IPD;
    /* ... 注意：SPL 的 GPIO_Init 会自动清 ODR 位，所以真正是下拉；
     *     这一步必须查标准库源码确认，否则会变成上拉输入而永远读到 1 */
}

/* 探针 3：拉地检测 —— 改成内部上拉输入，读到 0 说明被硬拉在地 */
uint8_t MyIIC_ProbeForcedLow(void)
{
    GPIO_InitStructure.GPIO_Mode = GPIO_Mode_IPU;
    /* ... */
}
```

**一个必须查证的细节**：STM32F1 的输入上下拉方向由 **ODR 位**决定。
如果 `GPIO_Init` 在设置 IPD 模式时不清 ODR，而之前代码把 ODR 置成了 1，
引脚实际会变成**上拉输入**，探针将永远读到 1（假阳性）。
查 `Library/stm32f10x_gpio.c` 确认 SPL 确实处理了这一点后才能相信探针结果：

```c
/* Reset the corresponding ODR bit */
if (GPIO_InitStruct->GPIO_Mode == GPIO_Mode_IPD)
{
  GPIOx->BRR = (((uint32_t)0x01) << pinpos);
}
```
