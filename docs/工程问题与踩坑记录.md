# 工程问题与踩坑记录

> 这份文档记录**开发过程中真实踩过的坑**，重点是**怎么定位的**而不是"最后怎么修的"。
> 写它的原因：跑通之后只留一个能跑的仓库，价值有限；出问题时的判断过程才是可复用的东西。
>
> AT24C02 那一段（三个叠加的硬件故障）单独写在 [`AT24C02-调试记录.md`](AT24C02-调试记录.md)。
> 本文记录其余的：Flash 分区溢出、编码取舍、下载工具链、以及框架层面的两个脆弱点。
>
> 日期：2026-09-20

## 一、BootLoader 溢出到 A 区，把自己擦掉（最严重的一个）

### 现象

用命令 `2` 通过 Xmodem 下载固件，**102 个数据包全部 ACK**、EOT 也确认了，
但复位之后板子**彻底没有反应**：串口一个字都不输出，OLED 保持上一帧不变，
**按复位键也无效** —— 只有用 ST-Link 重新烧录才能恢复。

这个现象特别容易误导人：传输阶段一切正常，所以第一反应会去查"跳转逻辑"或"Flash 写入"，
但那些都是对的。

### 定位过程

**第 1 步：确认芯片还活着**

用 Keil 重新烧录，`Erase Done / Programming Done / Verify OK` 全部通过 ——
**说明 MCU、供电、SWD 都没问题，是软件层面的状态坏了。**

**第 2 步：抓开机日志**

重新烧完 Keil 自动复位，串口打出：

```
No OTA update, jumping to region A
Jump to region A failed          ← boot.c 的 LOAD_A() 报的
```

`LOAD_A()` 的失败条件是 **`0x08005000` 处那 4 字节不是合法栈顶指针**
（不在 `0x20000000~0x20004FFF`）—— 也就是 **A 区是空的**。

**第 3 步：量镜像实际大小（关键一步）**

到这一步为止，还只能解释"A 区没写进去"。真正破案的是这一条命令：

```
fromelf --bin --output boot.bin Objects/Project.axf
→ 24124 字节
```

而分区定义里 `MyFlash_B_Page_Num = 20`，**B 区容量 = 20 × 1024 = 20480 字节**。

**24124 > 20480，溢出 3644 字节。**

### 根因

BootLoader 从 `0x08000000` 起占 24124 字节 → 一直延伸到 **`0x08005E3B`**，
而 **A 区从 `0x08005000` 开始** —— 中间这 **3644 字节的重叠区**，
存放的是链接器排在最后的那部分代码（`main()` 和自检诊断函数就在那儿）。

而命令 `2` 进门第一件事是：

```c
MyFlash_EraseFlash(MyFlash_A_Start_Page, MyFlash_A_Page_Num);   // 从 0x08005000 起擦 44 页
```

**于是每执行一次命令 2，BootLoader 就把自己的代码擦掉一截。**

- 传输阶段还能撑住（那条路径上的函数不在被擦区域）→ 102 包全 ACK 正常
- `NVIC_SystemReset()` 复位 → BootLoader 重新跑 → 一进 `main()` 就踩进被擦区域
  → **HardFault → 死循环 → 表现为"完全死机、复位键都没用"**

### 为什么会溢出

给 BootLoader 加**上电硬件自检**和**AT24C02 诊断工具**之后，ROM 占用从原来的十几 KB
涨到了 24124 字节。**加代码的时候没有检查分区容量。**

而链接器只按 `LR_IROM1` 的 start/size 做检查 —— 分区容量写错了它照样报"链接成功"。

### 修复

分区重新规划：**B 区 20KB → 32KB，A 区 44KB → 32KB**。要同步改的地方有四处，漏一处就出怪问题：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `6-串口IAP功能/User/main.h` | `MyFlash_B_Page_Num` 20 → 32 |
| 2 | A 区工程 `.uvprojx` 的 `<OCR_RVCT4>` | 起始 `0x08005000` → `0x08008000`，大小 → `0x8000` |
| 3 | A 区工程 `Start/system_stm32f10x.c` | `VECT_TAB_OFFSET` `0x5000` → `0x8000` |
| 4 | B 区工程 `.uvprojx` 的 `<OCR_RVCT4>` | 大小 → `0x8000` |

修复后 BootLoader 占 24124 字节 / B 区 32768 字节，**余量 8644 字节**。

### 教训

> **链接成功 ≠ 装得下。**

分区的容量必须和镜像实际大小**对账**。加了任何代码之后都要重新核：

```
fromelf --bin --output x.bin Objects/Project.axf     # 量实际 ROM 占用
# 跟 MyFlash_B_Page_Num × 1024 比较，留足余量
```

**另一个附带发现**：两个工程的 `IROM1` 原来都写成 `0x10000`（64KB），
导致 Keil 下载 BootLoader 时会把**整个 64KB 全擦掉、A 区跟着一起没**
（这正是"烧完 A 区程序板子就死"的原因）。改成正确的分区大小后，
Keil 只擦对应的扇区，A 区能保住。

## 二、编码取舍的三次反复

### 背景约束（实测确认）

**ARMCC 把源码字节原样写进 `.o` 文件** —— 字符串字面量的编码 **= 源码文件的编码**。
我用 6 组对照实验验证过（`UTF-8` / `UTF-8+BOM` / `--locale=english` / `--locale=chinese` /
`--multibyte_chars` / GBK 源码），**没有任何编译选项能在编译期转换字符串编码**：

| 源码编码 | .o 里字符串的字节 | 串口助手按 GB2312 看 |
|---|---|---|
| UTF-8（带不带 BOM 都是） | UTF-8 | ❌ 乱码 |
| GBK | GBK | ✅ 正常 |

### 三次反复

| 阶段 | 决定 | 动机 | 问题 |
|---|---|---|---|
| 1 | 源码统一 **UTF-8 + BOM** | GitHub 上中文注释能正常显示 | **串口中文变乱码** |
| 2 | 串口字符串**全改 ASCII 英文**（89 条） | 当时以为"上位机终端只支持 GB2312"，那就让输出不依赖编码 | 串口变英文，和教程不一致 |
| 3 | 改用 **UTF-8 终端**（Tera Term），字符串**改回中文** | 终端支持 UTF-8 之后，前提不成立了 | —— |

**第 3 步是最终方案**：源码 UTF-8 → 串口输出 UTF-8 → 终端设 UTF-8 看中文。
**GitHub 的中文注释和串口的中文输出可以同时成立**，不用二选一。

### 教训

> **结论依赖前提。前提变了，结论就必须重推。**

我在第 2 步给出的判断是"源码 UTF-8 和串口中文**不可兼得**"—— 那个结论的**前提**是
"上位机终端只支持 GB2312"。用户提出"Tera Term 支持 UTF-8"之后，前提不成立，
结论自然要改。

**另一个教训更实际**：**改动之前先问清楚环境能力，别急着改 89 条字符串。**
第 2 步如果先花两分钟确认端子支持什么编码，那 89 条字符串根本不用动。

### 顺带解决的编译问题

`ARMCC5` 默认按系统 ANSI 代码页解码源文件。**UTF-8 无 BOM 时**，中文字符串字面量会与
后续 ASCII 字节跨字符配对，报 `invalid multibyte character sequence`，
甚至吞掉结尾引号导致 `missing closing quote` 编译失败。

**加 UTF-8 BOM 即可解决，不需要任何编译选项。** 含非 ASCII 的 `.c/.h` 一律带 BOM；
`.uvprojx`（XML）和 `.s`（armasm）不加，避免风险。

## 三、串口下载工具链踩的坑

Xmodem-CRC 是嵌入式固件下载的通用做法，但**上位机工具的支持参差不齐**：

| 工具 | 情况 |
|---|---|
| **Tera Term** | ✅ **最终采用**。`文件 → 传输 → XMODEM → 发送`，协议选 `XMODEM`（非 1K）、校验选 `CRC`（非 Checksum） |
| **Xshell 8** | ⚠️ 菜单里有 X/YMODEM（能选 128 字节包），但**文件选择对话框读不到文件**（一直显示 0 KB）。中文路径下反复重试都不行 |
| **SSCOM** | ❌ **没有 Xmodem**，只有"发送文件"（裸字节流，无帧结构、无 ACK）—— 传不动 |

### 两次选错对话框

**第一次**：用 SSCOM 的"发送文件"发 bin —— 那是裸字节流。
BootLoader 等的是 `SOH(0x01) + 序号 + 反序号 + 128字节 + CRC16` 的 133 字节帧，
裸字节流里没有帧结构，**一包都不会被接受**（板子只会继续一遍遍发 `C`）。

**第二次**：在 Tera Term 里点成了 `文件 → 发送文件`（同样是裸发送），
而不是 `文件 → 传输 → XMODEM → 发送`。**两者对话框长得完全不同**，
Xmodem 那个才有协议/校验选项，是靠这个特征分辨出来的。

### 教训

> 用 Xmodem 之前先确认工具**真的有**这个功能，以及**点对了菜单**。
> 判断依据很简单：**弹出的对话框里有没有"协议/校验方式"选项** —— 有才是 Xmodem。

## 四、事件环形缓冲只有 10 个槽位（自动化脚本踩的）

### 现象

写了个 Python 脚本自动完成"发 `w` 进菜单 → 发 `2` → Xmodem 传输"的编排。
结果：**能进 Xmodem 模式、能收到 `C` 握手，但第 1 个数据包一直超时** ——
既没有 ACK 也没有 NAK，完全是静默。

### 定位

关键在**"超时而不是 NAK"**这个区别：

- CRC 校验失败 → BootLoader 会回 **NAK（`0x15`）**
- 完全没回应 → 说明那个 133 字节的包**根本没被当成一个完整包收下**

于是去看接收路径，找到了 `usart.h` 里的一行：

```c
#define Num 10    //se指针对结构体数组长度
```

**事件环形缓冲只有 10 个槽位（实际可用 9 个）。**

再看 `main.c` 的结构：

```c
OLED_Init();  MyIIC_Init();  USART1_Init();  AT24C02_ReadOTAInfo();  W25Q64_Init();
HW_SelfTest();
BootLoader_Branch();     // ← 里面的 BootLoader_Enter(50) 是纯延时轮询，死等 5 秒
while(1) { ... }         // ← 主循环从这里才开始，前面根本没人消费事件
```

**那 5 秒里主循环没跑、事件没人消费。** 而脚本每 300ms 发一个 `w`，
5 秒发了 17 个 —— **10 个槽位的环形缓冲被冲爆**，`In` 指针绕回去覆盖了
尚未消费的槽位（里面存着 `start`/`end` 指针），之后 `datalen` 算成垃圾值，
数据包被静默丢弃。

### 修复

- **脚本侧**（立即）：`w` 最多发 2 次，并且**判据改用接收方的 `C`**，
  而不是"等菜单文本出现"（板子已经在菜单里时不会再重打一遍菜单，等文本永远等不到）
- **固件侧**（本次）：`Num` 10 → 32，把窗口撑大（RAM 代价 256 字节）

### 教训

> **诊断信息的"有无"和"类型"同样重要。**
> "超时（完全没回应）"和"收到 NAK"指向完全不同的方向 —— 前者是包没被识别，
> 后者是包识别了但内容错了。**如果只看"传不动"这三个字，会一直在协议层打转。**

> **帧结构设计上没有"长度不匹配就丢弃"的容错**，是这次卡壳的深层原因 ——
> 见下一节。

## 五、命令解析严格匹配长度（脆弱点，本次已修）

### 问题

`BootLoader_Event()` 用**精确长度**判断命令：

```c
if((datalen == 1) && (data[0] == '1'))     // 菜单命令必须正好 1 字节
if(datalen == 26)                          // 版本号必须正好 26 字节
```

而串口工具**默认会补 `\r\n`** —— 发 `1` 实际是 3 字节，长度对不上，
命令被**静默忽略**，什么提示都没有。排查时很容易卡在"发了没反应"上。

### 修复

在 `BootLoader_Event()` 开头裁掉末尾的 `\r\n`：

```c
/* 但不能动 Xmodem 数据包 —— 那是二进制，尾字节可能就是 0x0D/0x0A，裁掉会让 CRC 校验失败 */
if((BootStaFlag & IAP_XMODEMData_FLAG) == 0)
{
    while((datalen > 0) && ((data[datalen-1] == '\r') || (data[datalen-1] == '\n')))
        datalen --;
}
```

**这里有个容易踩的坑**：不能无差别裁剪。Xmodem 数据包的最后一个字节是 CRC 低字节，
**完全可能就是 `0x0D` 或 `0x0A`**，裁掉就会导致 CRC 校验失败。
所以必须排除 Xmodem 分支。

### 教训

> 面向人工输入的命令解析，**要容忍人类和工具都会做的事**（补换行）。
> 严格匹配长度本身没错，但**失败时必须给出提示**，否则就是在制造"发了没反应"的黑洞。

## 六、Xmodem 尾包写入固定 4 页（本次已修）

### 问题

收到 EOT 后，剩余不足一个 1KB 扇区的数据要补写进 W25Q64：

```c
for(i = 0; i < 4; i++)    // ← 固定写 4 页（4×256 = 1024 字节）
{
    W25Q64_PageProgram((XmodemNum/8) * 4 + i + BlockNum*64*4, &UpDataBuff[i*256], 256);
}
```

但实际剩余可能只有 128 字节（半页）。**固定写 4 页会把 `UpDataBuff` 里残留的旧包
也写进 W25Q64。**

### 为什么之前没暴露

`FileLen` 只记录有效长度（`XmodemNum × 128`），搬运时也只读这个范围，
**所以多余部分是"写了但永远不会被读到"** —— 现象上完全没有影响。

### 修复

按实际数据量算页数：

```c
uint16_t rem = (UpDataA.XmodemNum % 8) * 128;   // 剩余字节
uint16_t pages = (rem + 255) / 256;             // 一页 256 字节
for(i = 0; i < pages; i ++)
```

### 教训

> **"暂时没有影响"和"正确"是两回事。**
> 这个 bug 被 `FileLen` 这个"外部约束"掩盖了 —— 一旦以后有人改成按整块读取，
> 立刻就会读到脏数据。**依赖外部约束掩盖的 bug，应该在还能安全修改的时候就修掉。**

## 七、汇总：这次的几条方法论

| 教训 | 具体体现 |
|---|---|
| **先量化，再判断** | 三个根因全靠量化定位：镜像长度 vs 分区容量、器件地址扫描、6 组编码对照实验 |
| **链接成功 ≠ 装得下** | 分区容量必须和镜像实际大小对账，链接器不会替你检查 |
| **结论依赖前提** | "UTF-8 和串口中文不可兼得"的前提是"终端只支持 GB2312"，前提变了结论就得改 |
| **一次只改一个变量** | 曾经同时让用户对调 SCL/SDA **并**更换杜邦线，结果根因永远无法归因 |
| **诊断工具本身也要验证** | I2C 探针用 `GPIO_Mode_IPD`，但 STM32F1 的上下拉方向由 ODR 位决定 —— 必须查标准库源码确认它会清 ODR，否则探针恒读 1（假阳性） |
| **区分"没回应"和"回应了但内容错"** | 前者是包没被识别，后者是协议层问题 —— 方向完全不同 |
| **失败必须可见** | 命令长度不匹配时静默忽略，是"发了没反应"的典型黑洞 |

### 关于"绕路"

这份文档里记了不少**走了弯路**的事（编码改了又改回去、工具试了三个、
诊断工具自己出过假阳性）。**这些不是需要藏起来的部分** ——
最终方案的价值有限，**判断过程**才是能复用的：

- 编码那一段，暴露的是"**没先确认环境能力就动手改代码**"
- 工具那一段，暴露的是"**没先确认工具真的支持这个协议**"
- 假阳性那一段，暴露的是"**用了一个自己没验证过的测量手段**"

三者其实是同一类错误：**没有先确认前提，就开始干活。**
